# Архитектура «Дом: проблема решена»

## Поток данных

~~~text
MAX update (Long Polling: личка, чат дома, кнопки)
    │
    ▼
MaxBotClient
    │
    ▼
BotApplication
  core      маршрутизация, черновики, outbox, фоновые задачи
  resident  житель и председатель
  staff     диспетчер и исполнитель
  admin     администратор УК и сервиса
    │
    ▼
IssueService + Directory ── правила объединения, голосование, оповещения, метрики
    │
    ▼
Repository ── PostgreSQL в Docker; SQLite и in-memory в тестах
~~~

Обработчики синхронно меняют данные и кладут сообщения в
очередь `outbox`; после ответа автору действия очередь рассылается — так автор
получает ответ первым, а сбой доставки одному адресату не мешает остальным.

## Модель данных

| Сущность | Таблица | Назначение |
|---|---|---|
| Organization | organizations | управляющая компания |
| StaffMember | staff | сотрудник: admin / dispatcher / master |
| House | houses | дом справочника: адрес, ключ адреса, подъезды, координаты, председатель, чат |
| Resident | residents | житель: дом, подъезд, согласие, настройки оповещений |
| StaffInvite | staff_invites | одноразовая ссылка сотрудника или председателя |
| Issue | issues | общая заявка: участники, голоса, срок, исполнитель, фото |
| IssueEvent | issue_events | журнал событий — источник метрик |
| Announcement | house_announcements | объявления УК по дому |
| — | drafts | состояние многошаговых диалогов |

Схема строится из dataclass-сущностей (`app/store.py`): при старте создаются
таблицы и добавляются недостающие колонки, поэтому базы прошлых версий
мигрируют без потери данных.

## Правило объединения

Похожая заявка — та же категория в том же доме из справочника, созданная не
более 72 часов назад и ещё открытая (новая или в работе). Для категорий с
охватом «подъезд» (лифт, свет, мусоропровод) дополнительно совпадает подъезд;
для охвата «дом» (протечка, отопление, двор, уборка) — нет. «Другое» не
объединяется. Бот не объединяет молча: житель выбирает «У меня тоже» или «Это
другая проблема».

## Подтверждение

- УК отмечает выполнение → статус «ожидает подтверждения жителей», голоса
  обнуляются.
- Итог наступает, когда больше половины участников ответили одинаково, или
  ответили все (при равенстве — «оспорено»). Голос председателя совета дома
  решает сразу.
- На середине `CONFIRMATION_TIMEOUT_MINUTES` молчащим — напоминание; по
  окончании решает большинство ответивших, а без ответов — «выполнено УК,
  подтверждение не получено».
- «Оспорено» возвращает заявку в очередь и увеличивает `dispute_count`;
  повторное оспаривание эскалируется и открывает жителям официальный канал.

## Массовые оповещения

После создания заявки жители того же подъезда (охват «подъезд») или дома
(охват «дом») с согласием и включёнными оповещениями получают сообщение с
кнопками «У меня тоже» / «Не касается» / «Не присылать». Лимит — 3 оповещения в
день на жителя. Если УК подключила чат дома (`/link КОД` в чате), оповещение
дублируется туда со ссылкой на личный диалог с ботом.

## Приоритет и сроки

Приоритет = вес категории × 10 + 5 за каждого присоединившегося + часы
ожидания / 3 (до 24) + 20 при просрочке. Сроки по категориям — ориентиры по
умолчанию (`CATEGORIES` в `app/domain.py`). Просрочка уведомляет УК и жителей
один раз.

## Ссылки `start`

- `h_<дом>_<подъезд>` — QR-плакат подъезда;
- `join_<заявка>` — приглашение соседа в заявку;
- `staff_<код>` — приглашение сотрудника или председателя.

## Надёжность

- Long Polling передаёт `marker`, события не обрабатываются повторно.
- Нажатие кнопки редактирует исходное сообщение; при ошибке — новое сообщение.
- Фото, которое MAX не принял, отбрасывается, карточка уходит без него.
- Загруженный плакат отправляется с повторами (`attachment.not.ready`); если
  загрузка не удалась — приходит ссылка.
- Черновики диалогов в БД: перезапуск посреди сценария ничего не ломает.
